# E-PocketBase — 미니PC(윈도우) 배포

`E-PocketBase/`(라즈베리파이 리허설 버전)를 **회사 12층 미니PC(Windows 10)** 에 올리는 배포 폴더입니다.

## 이 폴더의 성격

- **앱 본체는 여기에 없습니다.** 예약 화면(`pb_public/`)과 DB 스키마(`pb_migrations/`)는
  플랫폼 무관이므로 `../E-PocketBase/` 한 벌만 유지하고, 설치 시 그쪽에서 복사해 옵니다.
  (두 벌로 복제하면 화면 수정 시 한쪽만 고쳐지는 사고가 납니다)
- 이 폴더에는 **윈도우 전용 배포 수단**만 둡니다. 파이의 `install.sh`/`update.sh`에 대응하는
  윈도우판입니다.

| 파일 | 역할 | 파이 쪽 대응물 |
|---|---|---|
| `install.ps1` | 설치 + 소스 갱신 + 자동시작 등록 (멱등, 재실행 = 업데이트) | `install.sh` + `update.sh` |
| `설치방법.md` | 이 문서 | `설치방법.md` |

## 배경 — 왜 미니PC인가

- 회사 10층·12층은 IP 대역(게이트웨이)이 분리되어 있고, 층간 파일공유(`\\`)가 안 됨
- 미니PC는 12층에 있고 12층 IP를 받음: **192.168.2.86** (게이트웨이 192.168.2.1)
- 랜선 2개(양쪽 층 동시 연결)는 물리적으로 불가 — 케이블을 한곳으로 모을 수 없음
- **핵심 검증 과제**: 12층에 서버를 두면 10층에서도 접속되는가?
  - `\\`(SMB)가 막힌 것과 IP 라우팅이 없는 것은 별개 문제. HTTP는 될 수도 있음
  - 이 테스트 결과가 배포 방향을 결정함 (아래 "접속 테스트" 참조)

### IP 발급 방식 — MAC 등록제 (2026-07-29 확인)

이 회사는 **MAC 주소를 등록해야 IP가 나온다.** 미니PC의 MAC 으로 10층·12층 양쪽에서
각각 IP를 받아 두었다.

여기서 따라오는 사실 두 가지:

- **IP가 사실상 고정이다.** 재부팅해도 주소가 바뀌지 않으므로, 즐겨찾기·QR·인쇄물에
  주소를 박아도 안전하다. (일반 DHCP였다면 주소가 바뀌어 전부 무효가 될 수 있었다)
- **양쪽 IP를 받아둔 것이 "양쪽에서 접속된다"는 뜻은 아니다.** 랜선이 하나라 미니PC는
  한 번에 한 층에만 붙어 있다. 12층에 꽂혀 있는 동안 10층 IP는 응답하지 않는다.
  10층 사용자가 12층의 서버에 닿으려면 **층간 라우팅**이 있어야 하고, 그건 아직 미확인이다.

즉 MAC 등록은 주소 안정성 문제를 해결해 줄 뿐, 층간 접속 문제는 그대로 남아 있다.

## 설치 (관리자 PowerShell)

```powershell
cd <저장소>\E-PocketBase_minipc
powershell -ExecutionPolicy Bypass -File install.ps1
```

PocketBase 0.39.9(파이와 동일 버전 고정) 다운로드 → 앱 파일 복사 →
방화벽 8090·ping 허용 → 부팅 자동시작(작업 스케줄러 `vibres`, SYSTEM 계정) →
기동·헬스체크까지 자동입니다.

### 미니PC 앞까지 갈 필요는 없다

12층 데탑(192.168.2.24)에서 미니PC 로 **원격 데스크톱이 열린다** (3389, 2026-07-30 확인).

```powershell
mstsc /v:192.168.2.86
```

RDP 세션 안에서 관리자 PowerShell 을 띄우면 위 설치가 그대로 된다. 단
**저장소는 미니PC 안에 있어야 한다** — `install.ps1` 은 자기 옆의 `..\E-PocketBase` 를
읽으므로 다른 PC 의 경로를 참조할 수 없고, SMB(445)는 같은 층에서도 막혀 있어
네트워크 복사가 안 된다. RDP 안에서 `git clone` / `git pull` 하거나 RDP 드라이브
리다이렉션으로 옮긴다.

WinRM(5985)은 닫혀 있어 원격 PowerShell 로는 설치할 수 없다.

- 설치 위치: `C:\vibres\` (저장소 바깥 — 데이터와 소스를 분리)
- 예약 데이터: `C:\vibres\pb_data\` — install.ps1은 이 폴더를 절대 건드리지 않음
- 소스(화면) 갱신: 저장소에서 `git pull` 후 `install.ps1` 재실행

## 접속 테스트 — 출근해서 이 순서대로

**미니PC는 12층에 꽂아둔 채로 둔다.** 옮기면서 테스트하면 무엇 때문에 되고 안 되는지
구분할 수 없다. 10층 테스트는 *10층에 있는 다른 PC*에서 한다.

### 0단계 — 미니PC에서 (한 번만)

```powershell
# 관리자 PowerShell
cd <저장소>\E-PocketBase_minipc
powershell -ExecutionPolicy Bypass -File install.ps1
ipconfig | findstr IPv4          # 12층 IP가 192.168.2.86 이 맞는지 확인
```

방화벽 8090 개방과 부팅 자동시작이 여기서 함께 걸린다. 이걸 안 하면 밖에서는
절대 안 보인다.

### 1단계 — 12층 다른 PC에서

```
http://192.168.2.86:8090
```

**이 단계를 건너뛰지 말 것.** 여기서 되면 "윈도우 방화벽은 열렸다"가 확정되고,
다음 10층 결과가 순수하게 층간 라우팅 문제로 좁혀진다. 이걸 안 하고 10층에서
실패하면 방화벽 탓인지 라우팅 탓인지 알 수 없어 원점으로 돌아간다.

### 2단계 — 10층 PC에서 ← 배포 방향을 결정하는 지점

```
http://192.168.2.86:8090
```

안 되면 원인을 좁힌다:

```powershell
Test-NetConnection 192.168.2.86 -Port 3389     # 층간 통신 자체가 되는가
Test-NetConnection 192.168.2.86 -Port 8090     # 8090 만 막힌 것인가
tracert -h 5 192.168.2.86                      # 어디서 끊기는가
ping 192.168.2.86                              # 보조 — 아래 주의 참조
```

> **ping 실패를 "라우팅 없음" 으로 읽지 말 것.** 윈도우는 ICMP 를 기본 차단한다.
> 2026-07-30 **같은 12층 서브넷**의 데탑(192.168.2.24)에서 미니PC 로 보낸 ping 이
> 실패했다 — 라우팅은 멀쩡했고 3389 은 열려 있었다. `install.ps1` 이 ICMP 허용
> 규칙을 넣도록 고쳤지만, 경로 중간 장비가 ICMP 를 막으면 여전히 실패한다.
> **"패킷이 층을 넘는가" 는 3389 으로 판정한다.**

### 결과 기록

| 확인 위치 | 방법 | 결과 | 날짜 |
|---|---|---|---|
| 미니PC 자신 | http://127.0.0.1:8090 | ✅ 정상 | 2026-07-29 |
| 12층 데탑 (192.168.2.24) | `Test-NetConnection 192.168.2.86 -Port 3389` | ✅ 열림 | 2026-07-30 |
| 12층 데탑 (192.168.2.24) | `ping 192.168.2.86` | ❌ TimedOut (ICMP 기본 차단) | 2026-07-30 |
| 12층 데탑 (192.168.2.24) | `Test-NetConnection 192.168.2.86 -Port 445` | ❌ 막힘 (같은 층에서도 SMB 불가) | 2026-07-30 |
| 12층 데탑 (192.168.2.24) | http://192.168.2.86:8090 | 【 】 install.ps1 실행 후 | |
| 10층 PC | http://192.168.2.86:8090 | 【 】 | |
| 10층 PC | `Test-NetConnection 192.168.2.86 -Port 3389` | 【 】 | |

### 판정

| 12층 | 10층 | 뜻 | 다음 |
|---|---|---|---|
| ✅ | HTTP ✅ | 층간 HTTP 라우팅 있음 | **사내 자체호스팅 확정.** 미니PC 하나로 끝 |
| ✅ | 3389 ✅ / HTTP ❌ | 통신은 되는데 포트가 막힘 | 전산팀에 8090 개방 요청 — 해결 가능성 있음 |
| ✅ | 3389 ❌ | 층간 라우팅 없음 | Cloudflare 라이브 버전으로 (`01.클라우드(외부) 호스팅/`) |
| ❌ | ❌ | 미니PC 방화벽·서비스 문제 | 라우팅 판단 불가. 0단계부터 다시 |

### 함께 확인해두면 좋은 것 (메일용)

```powershell
Test-NetConnection smtp.hiworks.com -Port 465   # 사내에서 메일 발송이 되는가
Test-NetConnection 8.8.8.8 -Port 443            # 인터넷 자체는 되는가
```

`TcpTestSucceeded : True` 면 그 경로가 열린 것이다. 메일은 예약 기능의 전제가
아니므로 결과와 무관하게 예약은 동작하지만, 알림 방식(하이웍스 SMTP 직결 vs
HTTPS 메일 API)이 이 결과로 갈린다.
