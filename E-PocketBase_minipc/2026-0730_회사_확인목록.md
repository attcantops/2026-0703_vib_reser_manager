## 계획 변경 — 방향을 뒤집었다 (2026-07-30 13:10)

원래는 "서버를 12층에 고정하고 10층의 *다른 PC* 로 접속" 이었다. 그런데 미니PC 를
10층으로 가지고 내려가게 되어, 12층에 남는 서버가 없어진다.

그래서 **12층 데탑(192.168.2.24)에 판정용 임시 서버를 세웠다.** 미니PC 가 10층에
도착하면 미니PC 자신이 10층 클라이언트가 되어 `192.168.2.24:8090` 을 시험한다.
질문은 그대로다 — **10층 클라이언트가 12층 서버의 8090 에 닿는가.**

이 방식이 오히려 낫다. 10층에 사람이 가 있는 동안 12층에 사람이 없어도 되고,
미니PC 의 Claude Code 가 판정까지 직접 끝낼 수 있다.

| 확인 위치 | 방법 | 결과 |
|---|---|---|
| 12층 데탑 자신 | http://192.168.2.24:8090/ | ✅ HTTP 200 (화면 버전 `16edd02 (07-30 13:10)`) |
| 12층 데탑 | 방화벽 `vibres 8090` · `vibres ICMPv4` | ✅ 둘 다 Enabled |
| 12층 데탑 | 작업 스케줄러 `vibres` | ✅ Running · 부팅 자동시작 |

> **데탑 서버는 판정용 임시다.** 예약 데이터(`C:\vibres\pb_data`)가 미니PC 와 별개로
> 생긴다. 여기에 실제 예약을 넣으면 그 기록은 미니PC 로 옮겨가지 않는다. 판정이
> 끝나면 내린다 (아래 "데탑 임시 서버 철거").

### 이 방향으로 놓치는 것 — 반대 방향은 따로 확인해야 한다

이 시험은 **10층 → 12층** 을 증명한다. 그런데 실서버(미니PC)가 10층에 남는다면
운영 시 필요한 것은 **12층 → 10층** 이다. 라우팅은 보통 대칭이지만 ACL 은
한 방향만 막을 수도 있다. 그래서 미니PC 가 10층에 자리 잡은 뒤,
**12층 데탑에서 미니PC 의 새 10층 IP 로 한 번 더 확인한다.**

```powershell
# 12층 데탑에서, 미니PC 의 10층 IP 를 넣어 실행
Test-NetConnection <미니PC-10층-IP> -Port 8090
```

미니PC 가 10층에서 받은 IP 를 먼저 알려줘야 한다 (`ipconfig | findstr IPv4`).

### 데탑 임시 서버 철거 (판정 끝난 뒤)

```powershell
Stop-ScheduledTask     -TaskName vibres
Unregister-ScheduledTask -TaskName vibres -Confirm:$false
Get-Process pocketbase -ErrorAction SilentlyContinue | Stop-Process -Force
Remove-NetFirewallRule -DisplayName "vibres 8090"
Remove-NetFirewallRule -DisplayName "vibres ICMPv4"
Remove-Item -Recurse -Force C:\vibres      # 데탑 쪽 예약 데이터도 함께 사라진다
```

## 2단계 — 10층 PC에서 ← 여기가 결론

```
http://192.168.2.86:8090
```

- [ ] 열린다  /  - [ ] 안 열린다

**안 열리면** 원인을 좁힙니다. PowerShell에서:

```powershell
Test-NetConnection 192.168.2.86 -Port 3389    # 패킷이 층을 넘는가  ← 라우팅 판정
Test-NetConnection 192.168.2.86 -Port 8090    # 8090 만 막힌 것인가
tracert -h 5 192.168.2.86                     # 어디서 끊기는가
ping 192.168.2.86                             # 보조 — 아래 주의
```

- [ ] 3389 `TcpTestSucceeded`: True / False  ← **라우팅 판정은 이걸로**
- [ ] 8090 `TcpTestSucceeded`: True / False
- [ ] `tracert` 가 끊기는 지점: `________________`
- [ ] `ping` 응답: 있음 / 없음 (보조 정보)

> **ping 실패를 "층간 라우팅 없음" 으로 읽지 마세요.**
> 윈도우는 ICMP 를 기본 차단합니다. 2026-07-30 **같은 12층 서브넷**의 데탑
> (192.168.2.24)에서 미니PC 로 ping 을 보냈더니 실패했습니다 — 라우팅은 멀쩡하고
> 3389 은 열려 있었습니다. 즉 ping 실패는 아무것도 증명하지 못합니다.
>
> `install.ps1` 이 이제 ICMP 허용 규칙을 함께 넣지만, 스크립트를 돌리기 전이거나
> 경로 중간 장비가 ICMP 를 막으면 여전히 실패합니다. **3389(원격 데스크톱)은
> 미니PC 에서 이미 열려 있으니, "패킷이 층을 넘는가" 는 이 포트로 봅니다.**

## 판정 — 결과에 따라 다음이 정해집니다

| 12층 | 10층 | 뜻 | 다음 |
|---|---|---|---|
| ✅ | HTTP ✅ | 층간 HTTP 라우팅 있음 | **사내 자체호스팅 확정.** 미니PC 하나로 양쪽 층 커버 |
| ✅ | 3389 ✅ / HTTP ❌ | 통신은 되는데 포트가 막힘 | 전산팀에 **8090 개방** 요청 — 해결 가능성 있음 |
| ✅ | 3389 ❌ | 층간 라우팅 자체가 없음 | **Cloudflare 라이브 버전**으로 전환 |
| ❌ | — | 미니PC 방화벽·서비스 문제 | 라우팅 판단 불가. 0단계부터 다시 |

두 번째와 세 번째를 구분하려고 **3389** 을 따로 봅니다.
**통신이 되는데 포트만 막힌 거면 협의로 풀릴 여지가 있고, 3389 도 안 닿으면 쉽게 안 풀립니다.**

판정 기준을 `ping` 에서 3389 으로 바꾼 이유는 위 2단계의 주의를 보세요. 한 줄로 줄이면:
**ping 실패는 라우팅이 없다는 증거가 되지 못합니다.** 같은 층에서도 실패했습니다.
