## 1. 이 시스템이 무엇인가

진동시험기를 여러 사람이 나눠 쓰기 위한 **예약 웹앱**입니다. 시간대별 그리드에서
빈칸을 골라 예약하고, 같은 장비·같은 시각의 중복을 원천 차단합니다.

### 왜 PocketBase인가

보통 이런 시스템은 DB 서버 + 웹 서버 + 인증 + 관리도구를 각각 구축해야 합니다.
PocketBase는 **실행파일 하나**에 SQLite·REST API·관리자 UI가 모두 들어 있습니다.

이 프로젝트에서 결정적이었던 이유는 두 가지입니다.

1. **외부 종속이 0** — 가입·계정·요금제가 없습니다. 회사 폐쇄망에서 인터넷 없이 동작합니다.
   (A안 구글시트는 구글 계정, C안 Supabase·D안 Vercel은 각 서비스 계정에 묶입니다)
2. **관리자 화면이 기본 제공** — 예약을 엑셀처럼 직접 보고 고칠 수 있습니다.
   A안에서 구글시트가 하던 역할을 `/_/` 화면이 대신합니다.

### 라즈베리파이의 위치

**최종 목적지는 회사 NAS입니다.** 파이는 리허설 무대입니다.
담당자에게 설치를 한 번만 부탁하고 이후에는 원격으로 운영한다는 시나리오를,
실제 장비에서 통째로 예행연습하는 것이 목적이었습니다.

## 3. 데이터 구조와 보안 설계

### reservations

| 필드 | 타입 | 필수 | 비고 |
|---|---|---|---|
| machine | text | O | 장비명 |
| date | text | O | `YYYY-MM-DD` (패턴 검증) |
| hour | number | — | 0~23 정수. 예약 시작 시각 |
| name | text | O | 예약자 |
| dept / memo / email | | X | 부서 / 메모 / 이메일 |

**중복 차단**: `(machine, date, hour)` UNIQUE 인덱스. 두 명이 동시에 같은 칸을 눌러도
DB 레벨에서 한 명만 성공합니다(나머지 HTTP 400).

> `hour`를 필수로 두지 않은 이유: PocketBase는 숫자 `0`을 빈 값으로 취급해서,
> 필수로 두면 **0시 예약이 거부**됩니다. 대신 컬럼이 `NUMERIC DEFAULT 0 NOT NULL`이라
> NULL이 발생할 수 없고, UNIQUE 인덱스도 정상 동작합니다(실측: 200 → 400).

### API 권한 — 가장 중요한 설계 전제

| 동작 | 규칙 | 의미 |
|---|---|---|
| 조회 (list/view) | `""` | **누구나** |
| 등록 (create) | `""` | **누구나** |
| 삭제 (delete) | `""` | **누구나** |
| 수정 (update) | `null` | 관리자만 (비인증 시도 HTTP 403) |

**이것은 사내 폐쇄망 전용 설계입니다.** 로그인 없이 편하게 쓰라고 의도적으로 연 것이고,
그 환경에서는 합리적입니다. 다만 **인터넷에 노출하는 순간 "주소를 아는 사람은 누구나
예약 전체를 삭제할 수 있다"** 가 됩니다. 앱 화면에서는 이름이 맞아야 취소되지만,
그건 화면상의 제약이고 API를 직접 부르면 통하지 않습니다.

## 4. 백업 체계

### 왜 이렇게까지 하나

SD카드는 언젠가 죽습니다. 24시간 켜두는 서버에서는 **정전으로 파일시스템이 깨지는 것**이
가장 흔한 고장입니다. 그리고 PocketBase 내장 자동백업은 저장 위치가 `pb_data` 안,
**즉 같은 SD카드**입니다. 그것만으로는 대비하려던 사고에 무력합니다.

### 전체 흐름 (종단 검증 완료)

```
파이   매일 03:10  vibres-backup.timer
                   └ sqlite3 .backup 으로 무정지 스냅샷 (data.db + auxiliary.db)
                   └ tar 무결성 확인 → /opt/vibres/backups-local/ (14개 보관)

PC     매일 03:30  작업 스케줄러 "VibresBackupPull"
                   └ 파이에서 새 파일만 회수 → tar -tzf 로 재검증
                   └ D:\backup\vibres\store\  (1차)
                   └ E:\backup\vibres\store\  (복제 — PC 디스크 1개가 단일 실패점이 되지 않게)
```

- **"예약 시간에 놓친 작업 실행"** 켜둠 — PC가 03:30에 꺼져 있어도 켜진 뒤 실행됩니다.
- 파이 → PC는 **끌어오는(pull)** 방식입니다. 윈도우에 SSH 서버가 없어 파이가
  밀어넣을 수 없기 때문입니다. 파이 `backup.conf`에 `EXTERNAL_PULL="1"`로 명시했습니다.
- ⚠️ `REMOTE`와 `EXTERNAL_PULL`이 **둘 다 비면 백업이 실패**하도록 두었습니다.
  설정이 없는 상태가 조용히 성공으로 넘어가면, "백업이 있다"는 착각만 남기 때문입니다.

### 복구 절차 (리허설 완료)

파이 백업을 **다른 장비**에 복원해 예약 0건 → 3건 복구를 확인했습니다.
"백업 파일이 있다"와 "복원된다"는 다릅니다.

```bash
sudo systemctl stop vibres
sudo mv /opt/vibres/pb_data /opt/vibres/pb_data.old
sudo mkdir -p /opt/vibres/pb_data
sudo tar xzf <백업파일>.tar.gz -C /opt/vibres/pb_data
sudo systemctl start vibres
```

## 5. 운영 런북

### 담당자에게 부탁할 것 — 최초 1회

```bash
curl -fsSL https://raw.githubusercontent.com/attcantops/2026-0703_vib_reser_manager/main/E-PocketBase/install.sh | sudo bash
```

아키텍처 판별 → PocketBase 설치 → systemd 등록 → 백업 타이머 등록 → 기동 확인까지 자동입니다.
끝나면 접속 주소를 출력합니다. **관리자 계정은 만들지 않으므로**, 운영자가 접속해서 처음 만듭니다.

### 이후 운영 (SSH 접속 후)

| 명령 | 용도 |
|---|---|
| `sudo /opt/vibres/update.sh` | 소스 갱신 + 재시작 (평상시 이것만) |
| `sudo /opt/vibres/update.sh --rollback` | 소스를 직전 커밋으로 되돌리기 |
| `sudo /opt/vibres/update.sh --pb` | PocketBase 실행파일 갱신 (고정 버전) |
| `sudo /opt/vibres/update.sh --rollback-pb` | 실행파일을 갱신 직전 버전으로 되돌리기 |
| `sudo /opt/vibres/backup.sh` | 백업 즉시 생성 |
| `sudo systemctl status vibres` / `journalctl -u vibres -f` | 상태 / 실시간 로그 |
| `sudo /opt/vibres/pocketbase --dir=/opt/vibres/pb_data superuser update <이메일> <비번>` | 비밀번호 변경 |

> `update.sh`는 **저장소 바깥**(`/opt/vibres/`)에 설치돼 있습니다.
> 저장소 안의 사본을 실행하면 `--rollback` 시 스크립트가 스스로 지워져 복구 수단이 사라집니다.

### PC 쪽 백업 작업

```powershell
Get-ScheduledTaskInfo -TaskName "VibresBackupPull"          # 상태 확인
Start-ScheduledTask -TaskName "VibresBackupPull"            # 즉시 실행
Get-Content D:\backup\vibres\pull-backup.log -Tail 20       # 로그
Unregister-ScheduledTask -TaskName "VibresBackupPull" -Confirm:$false   # 제거
```

⚠️ `D:\backup\vibres\pull-backup.ps1`은 **UTF-8 BOM으로 저장**되어야 합니다.
BOM이 없으면 Windows PowerShell 5.1이 한글을 깨서 읽어 파싱에 실패합니다.

### 검토가 틀렸던 것 (3건, 실측 반박)

| 지적 | 실측 결과 |
|---|---|
| `hour` NULL로 중복 차단 우회 가능 | 컬럼이 `NUMERIC DEFAULT 0 NOT NULL`. 시도1 `200` → 시도2 `400` 정상 차단 |
| `/etc/dhcpcd.conf` 잔재 방치 | 이미 주석 처리돼 있었음 (2~3행 `#`) |
| wlan0 autoconnect 미확인 | 재부팅 전 프로파일 목록에 `preconfigured:wlan0:yes` 출력됨 |

### 검토가 유발한 추가 발견 (1건)

지적을 반영하는 과정에서 **더 심한 버그**를 발견했습니다.

cron 등록 코드가 root 크론탭이 없는 장비에서 `crontab -l` 실패 → `set -e`로
**설치가 통째로 중단**됐습니다. 두 번째 실행부터는 크론탭이 생겨 통과하므로
**첫 설치에서만 재현**되고, 담당자 현장에서만 터질 형태였습니다.
cron 의존을 제거하고 systemd 타이머로 교체한 뒤, `crontab`이 아예 없는
컨테이너에서 첫 설치를 검증했습니다.

## 7. 남은 위험과 결정 사항

### 외부 공개 — 통로 문제가 아니라 설계 문제

"밖에서 폰으로 접속하고 싶다"는 요구는 통로를 뚫는 문제로 보이지만 아닙니다.
3장에서 본 대로 **삭제 권한이 공개**이기 때문입니다.

| 목적 | 방법 | 위험 |
|---|---|---|
| 폰 화면 확인만 | 폰을 집 WiFi에 연결 → `http://192.168.0.222:8090/` | **없음. 추가 작업 0분** |
| LTE에서 테스트 | Cloudflare Tunnel **+ Cloudflare Access(인증) 필수** | Access 없이는 열지 말 것 |
| 운영 중 사외 접속 | **앱 차원의 인증 설계가 선행** | 터널만으로는 해결 안 됨 |

> `trycloudflare.com` 주소는 **인증 없는 공개 HTTPS 주소**입니다.
> 터널이 개선하는 것은 집 IP 비노출과 HTTPS뿐이고, "누구나 전체 삭제 가능"은
> 포트포워딩과 완전히 동일합니다. 관리자 화면도 함께 노출됩니다.

⚠️ **공유기 포트포워딩으로 22번(SSH)을 여는 것은 하지 마세요.**
파이는 SSH 비밀번호 로그인이 허용돼 있고 `pi` 계정이 무암호 sudo(`NOPASSWD: ALL`)라,
뚫리면 장비 전체를 내주게 됩니다.

### 미결 사항

| 항목 | 내용 | 판단 |
|---|---|---|
| git 이력 재작성 | 커밋 `f8c4a68`에 테스트 계정 메모가 남아 있음 | 죽은 계정이라 본질은 **재사용 금지**. 하려면 커밋 12개인 지금이 가장 쌈. `update.sh`가 `fetch + reset --hard`라 재작성해도 파이는 그대로 따라옴 |
| SSH 공개키 정리 | `authorized_keys`에 **6개** 등록됨 | 예전 PC 키가 남아있을 수 있음. 한 번 점검 권장 |
| `/etc/dhcpcd.conf` | 주석 처리됨 (dhcpcd 서비스도 비활성) | 조치 완료. 참고용 기록 |

## 8. 이번에 확인된 방법론

다른 배포에도 적용할 만한 것들입니다.

1. **실기 전에 컨테이너 리허설.** systemd가 실제로 도는 `debian:12` 컨테이너에서
   설치 스크립트를 끝까지 돌렸더니 버그 3건이 나왔습니다.
   ```
   docker run -d --privileged --cgroupns=host -v /sys/fs/cgroup:/sys/fs/cgroup:rw \
     debian:12 /bin/bash -c "... && exec /sbin/init"
   ```
   특히 **첫 설치 경로**는 깨끗한 환경에서만 드러납니다.

2. **실행 형태 그대로 검증.** `curl | bash`에서 `apt-get`이 stdin(스크립트 본문)을
   삼켜 설치가 깨지는 버그는, 파일로 받아 실행했다면 끝까지 못 찾았을 문제입니다.

3. **HTTP 200만 보고 판단하지 말 것.** PocketBase는 없는 경로에 `index.html`을
   SPA 폴백으로 돌려줍니다. 실제로 SDK 파일이 없는데 200이 나왔습니다.
   **content-type까지 확인해야** 합니다.

4. **자기참조 함정.** 복구 스크립트가 복구 대상 안에 있으면, 롤백 시 스스로 사라집니다.
   `update.sh`를 저장소 바깥에 두는 이유입니다.

5. **"기록이 없다"와 "조치가 없다"는 다르다.** 검토 측 오류 3건 중 2건이 이 혼동에서
   나왔습니다. 반대로 구축 측은 조치해놓고 요약에 빠뜨린 항목이 있었습니다.
   양쪽 다 **실측으로만** 정리됐습니다.

## 9. 한 줄 요약

시스템은 동작하고, 운영 도구(설치·업데이트·롤백·백업·복원)까지 갖춰졌습니다.
**폐쇄망 실사용 기준으로는 준비가 끝난 상태**입니다.
남은 것은 기능이 아니라 판단입니다 — 외부 공개를 할 것인지, 한다면 인증을
어떻게 붙일 것인지. 폰 화면 확인이 목적이라면 집 WiFi로 오늘 끝납니다.
