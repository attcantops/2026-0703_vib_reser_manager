## 0. 먼저 — 유지해야 할 잘 된 판단

되돌리지 마시고 다른 배포에도 적용할 만한 것들입니다.

1. **`update.sh`를 저장소 바깥(`/opt/vibres/update.sh`)에 설치** — `--rollback`으로 스크립트가 없던 시점까지 되돌아가도 복구 수단이 살아남습니다. 놓치기 쉬운 자기참조 문제를 제대로 막았습니다.
2. **`curl | bash`에서 `apt-get`이 stdin을 삼키는 버그를 리허설로 발견** — 실제 실행 형태로 검증하지 않았으면 담당자 현장에서 터졌을 문제입니다.
3. **`pb_data`를 저장소 바깥에 배치** — `git pull`이 예약 데이터를 덮을 수 없는 구조입니다.
4. **접속 안내 IP를 `hostname -I` 대신 기본 경로 출발지로 변경** — 다중 인터페이스 환경에서 엉뚱한 주소를 안내하던 문제를 해결했습니다.

## 1. 즉시 조치 — 재부팅 관련

### 1-1. 폴백으로 삼은 WiFi가 부팅 시 살아난다는 근거가 없음

**문제**
재부팅 강행의 안전 근거가 "WiFi 프로파일은 건드리지 않았으니 유선이 실패해도 `192.168.0.6`으로 접속 가능"이었습니다. 그러나 **wlan0의 `autoconnect` 값을 확인한 기록이 없습니다.** `[추정]`

**왜 문제인가**
바로 직전에 eth0에서 *"지금 활성인 프로파일(autoconnect=no)과 재부팅 시 활성화될 프로파일(autoconnect=yes)이 서로 다르다"* 는 사실을 발견했습니다. `[확인]`
즉 **"지금 연결되어 있다"가 "부팅 후에도 연결된다"를 의미하지 않는 환경**임을 이미 겪었는데, 정작 안전망으로 지정한 인터페이스에는 같은 검사를 적용하지 않았습니다.

둘 다 올라오지 않으면 SSH 복구가 불가능하고, 파이에 모니터·키보드를 물리는 물리 접근이 필요합니다.

**조치**
```bash
# wlan0 프로파일의 자동연결 여부 확인 (재부팅 전이라면 먼저)
nmcli -t -f NAME,DEVICE,AUTOCONNECT connection show

# autoconnect 가 no 이면 켠다
sudo nmcli connection modify "<wlan0_프로파일명>" connection.autoconnect yes
sudo nmcli connection modify "<wlan0_프로파일명>" connection.autoconnect-priority 10
```
이미 재부팅했다면, 접속이 되는 상태에서 위를 확인해 **다음 재부팅**을 대비하세요.

### 1-2. eth0·wlan0가 같은 서브넷에 동시 존재

**문제**
`192.168.0.222`(유선)와 `192.168.0.6`(무선)이 같은 L2 세그먼트에 있고 게이트웨이도 동일합니다. `[확인]`
작업 중 ARP 혼선 가능성을 언급했으나 그대로 진행됐습니다.

**왜 문제인가**
리눅스는 기본값(`arp_ignore=0`)에서 **어느 인터페이스로 들어온 ARP 요청이든 로컬 IP 전부에 응답**합니다. `.222`로 향한 트래픽에 무선 MAC이 답하는 식의 혼선이 생길 수 있습니다.
증상이 "완전 불통"이 아니라 **"가끔 느리다 / 간헐적으로 끊긴다"** 로 나타나기 때문에 원인 추적이 어렵고, 예약 시스템에서는 사용자 신뢰를 잃는 형태의 고장입니다.

**조치 — 셋 중 하나**

| 선택지 | 내용 | 적합한 경우 |
|---|---|---|
| **A. 하나만 사용 (권장)** | 유선만 남기고 wlan0 비활성 | 실서버가 NAS라 파이는 검증용. 단순함이 최선 |
| B. ARP 동작 고정 | `arp_ignore=1`, `arp_announce=2` 설정 | 이중화를 꼭 유지해야 할 때 |
| C. 진짜 이중화 | active-backup 본딩 구성 | 무중단이 요구사항일 때 |

A안을 권합니다. 다만 **1-1 확인 전에는 wlan0를 끄지 마세요.** 유일한 복구 경로입니다.

### 2-1. 관리자 비밀번호가 임시 약한 값

**문제**
운영 설정 단계에서 설정된 관리자 비밀번호가 **추측 가능한 8자리 단순 문자열**입니다. `[확인]`
작업 중 스스로 *"관리자 비밀번호가 임시라 특히 위험합니다"* 라고 인지했으나 교체되지 않았습니다.

**왜 문제인가**
외부 공개 논의가 이 상태에서 진행됐습니다. 관리자 화면(`/_/`)이 노출되면 **데이터 전체 열람·삭제·스키마 변경**이 가능합니다. 이 비밀번호는 자동화된 대입 공격의 기본 사전에 포함됩니다.

**조치 (지금)**
```bash
sudo /opt/vibres/pocketbase --dir=/opt/vibres/pb_data superuser upsert <이메일> <강한비밀번호>
```
새 비밀번호는 **저장소·문서·채팅에 남기지 말고** 비밀번호 관리자에 보관하세요.

### 2-2. 공개 저장소 커밋 이력에 자격증명 잔존

**문제**
브라우저가 저장한 로그인 정보 파일이 공개 저장소에 커밋(`f8c4a68`)됐고, 이후 파일은 삭제됐으나 **이력에는 남아 있습니다.** `[확인]`
당시 평가는 *"임시 테스트 계정이라 실질적 위험은 없다"* 였습니다.

**왜 그 평가에 동의하지 않는가**
- GitHub 공개 저장소는 자격증명 스캐너가 상시 순회하며, 푸시 후 **수 분 내** 수집됩니다. 파일 삭제 시점과 무관합니다.
- 삭제 후에도 **커밋 SHA를 알면 웹에서 직접 접근**할 수 있습니다.
- `force push`로 이력을 재작성해도 GitHub는 orphan 커밋을 일정 기간 보관합니다. **완전 제거는 GitHub 지원팀에 GC를 요청해야 합니다.**

**조치**
1. 해당 비밀번호 문자열을 **다른 어떤 곳에서도 재사용하지 않기** (가장 중요)
2. 이력 재작성 여부 결정 — 하려면 `git filter-repo` 사용 후 GitHub 지원팀에 요청
3. 재발 방지: `.gitignore`에 `*.txt` 브라우저 저장 파일 패턴 추가 (완료된 것으로 보임) + **커밋 전 `git status` 확인 습관화**

### 2-3. 인증 없는 Cloudflare Tunnel은 포트포워딩과 동일한 노출

**문제**
외부 접속 방법을 `② Cloudflare Tunnel = 권장` / `③ 포트포워딩 = 비권장` 으로 구분해 안내했습니다. `[확인]`
**이 구분은 오해를 유발합니다.**

**왜 문제인가**
`pb_migrations`에서 확인된 실제 API 권한입니다. `[확인]`

| 동작 | 규칙 | 의미 |
|---|---|---|
| 조회(list/view) | `""` | 누구나 |
| 등록(create) | `""` | 누구나 |
| **삭제(delete)** | `""` | **누구나** |
| 수정(update) | `null` | 관리자만 |

`trycloudflare.com` 주소는 **인증 없는 공개 HTTPS 주소**입니다. 터널이 개선하는 것은 *집 IP 비노출* 과 *HTTPS* 뿐이고, **"주소를 아는 사람은 누구나 예약 전체를 삭제할 수 있다"** 는 핵심 위험은 포트포워딩과 완전히 동일합니다. 관리자 화면도 함께 노출됩니다.

**조치 — 목적에 따라**

- **폰 화면 확인만 필요하다면**: 외부 공개 불필요. 스마트폰을 집 WiFi에 붙여 `http://192.168.0.222:8090` 확인. **작업 0분, 위험 0.**
- **LTE에서 실제 접속 테스트가 필요하다면**: Cloudflare Tunnel + **Cloudflare Access(이메일 인증) 필수**. Access 없이는 열지 마세요.
- **운영 단계에서 사외 접속이 요구사항이라면**: 터널 이전에 **앱 차원의 인증 설계**가 선행돼야 합니다. `deleteRule` 공개는 폐쇄망 전제의 설계이며, 인터넷 노출과 양립할 수 없습니다.

## 3. 운영 — 배포 전 정리

### 3-1. 백업이 방어하려던 실패 모드를 방어하지 못함

**문제**
*"SD가 죽으면 그 안의 백업도 같이 죽습니다"* 라고 정확히 진단한 뒤, 실제로 활성화한 것은 **PocketBase 내장 자동 백업**입니다. `[확인]`
내장 백업의 저장 위치는 `pb_data` 내부, 즉 **같은 SD카드**입니다.

파이 외부로 복사하는 설정이 실제로 완료됐는지는 전사에서 확인되지 않습니다. `[추정]`

**왜 문제인가**
현재 상태는 "백업이 있다"는 **착각만 제공**합니다. 대비하려던 사고(SD 손상·정전)가 나면 원본과 백업이 함께 사라집니다.

**조치**
파이 밖으로 나가는 경로를 만들어야 완료입니다.
```bash
# 예: 매일 새벽 3시, pb_data 를 외부로 복사
sudo crontab -e
0 3 * * * tar czf /tmp/vibres-$(date +\%Y\%m\%d).tar.gz -C /opt/vibres pb_data && \
          scp /tmp/vibres-*.tar.gz <사용자>@<PC또는NAS>:<경로>/ && rm -f /tmp/vibres-*.tar.gz
```
- 파일이 MB 단위라 부담 없습니다.
- **복원 리허설까지 해야 검증 완료**입니다. 백업 파일 존재 확인만으로는 부족합니다.

### 3-2. 설치 버전이 고정되어 있지 않아 재현성이 없음

**문제**
`install.sh`가 GitHub API로 **매번 PocketBase 최신 버전을 조회해 설치**합니다. `[확인]`
```bash
PB_VERSION="$(curl -fsSL https://api.github.com/repos/pocketbase/pocketbase/releases/latest ...)"
```

**왜 문제인가**
- PocketBase는 **1.0 이전**이며, 실제로 **v0.23에서 컬렉션 API가 통째로 변경**된 전력이 있습니다. 마이그레이션 파일 주석도 *"대상 버전: PocketBase v0.23 이상"* 으로 버전 의존성을 명시하고 있습니다. `[확인]`
- 따라서 **오늘 설치한 것과 6개월 뒤 담당자가 설치하는 것이 다른 소프트웨어**입니다.
- 미래 버전이 또 깨는 변경을 하면 **지금까지의 리허설 결과가 그 설치에 대해 아무것도 보증하지 못합니다.** 검증의 의미를 무효화하는 구조입니다.

**조치**
검증이 끝난 버전을 기본값으로 고정하고, 올릴 때는 의도적으로 올립니다.
```bash
# install.sh
PB_VERSION="${PB_VERSION:-0.39.9}"   # 파이에서 검증 완료된 버전으로 기입
```
`설치방법.md`에도 "검증된 버전"으로 명시하고, 갱신은 `update.sh --pb` 경로로 다루면 됩니다.

**조치**
백업(`/root/net-backup-20260726`)이 있으므로 해당 블록을 주석 처리하고, 주석에 사유와 날짜를 남기세요.

## 4. 검증 필요 — 잠재 버그

### 4-1. `hour` 누락 시 중복 예약 차단이 우회될 가능성

**문제**
```js
{ name: "hour", type: "number", required: false, min: 0, max: 23, onlyInt: true }
indexes: ["CREATE UNIQUE INDEX ... ON reservations (machine, date, hour)"]
```
`hour`가 `required: false`인데 UNIQUE 인덱스의 구성 컬럼입니다. `[확인]`
**SQLite는 UNIQUE 인덱스에서 NULL을 서로 다른 값으로 취급합니다.**

만약 `hour` 누락 요청이 NULL로 저장된다면, 같은 장비·같은 날짜로 **중복 차단을 우회하는 행을 무제한 생성**할 수 있습니다.

PocketBase가 생략된 number 필드를 `0`으로 채우는지 `NULL`로 두는지에 따라 갈리므로 **단정할 수 없습니다.** `[추정]`
다만 API가 공개라 외부에서 시도 가능하고, 기존 API 검증은 `hour`를 정상 포함한 경로만 테스트했습니다. `[확인]`

**검증 방법**
```bash
# hour 없이 동일 요청 2회 — 두 번째가 400 이 아니면 우회 성립
for i in 1 2; do
  curl -s -o /dev/null -w "%{http_code}\n" \
    -X POST http://192.168.0.222:8090/api/collections/reservations/records \
    -H "Content-Type: application/json" \
    -d '{"machine":"__검증용__","date":"2026-12-31","name":"테스트"}'
done
```
- **정상**: `200` → `400`
- **버그**: `200` → `200`

버그로 확인되면 `hour`에 기본값을 부여하거나, 인덱스를 `COALESCE(hour, -1)` 기반 표현식 인덱스로 변경하는 방법이 있습니다.
검증 후 `__검증용__` 레코드는 삭제하세요.

## 6. 총평

기술적 실행력은 높습니다. 컨테이너 리허설로 실제 버그를 세 건 잡아냈고, 롤백 시 스크립트 자기소멸 같은 놓치기 쉬운 문제까지 설계 단계에서 막았습니다.

지적하고 싶은 것은 개별 기술 판단이 아니라 **위험 평가의 방향성**입니다.

- 자격증명 유출 → "실질적 위험 없음"
- 검증하지 않은 WiFi → "안전망 있음"
- 같은 카드 안의 백업 → "백업 설정 완료"
- 인증 없는 터널 → "권장"

각각은 작은 낙관이지만 **네 건의 방향이 모두 같습니다.** 리허설을 그토록 꼼꼼히 한 것과 대비되는 지점이고, 검증을 통과한 시스템이 검증되지 않은 가정 위에 놓이는 형태입니다.

권하는 순서는 **재부팅 안전 확보 → 비밀번호 교체 → 백업 외부화** 이며, 외부 공개는 이 셋이 끝난 뒤에 인증을 붙여서 진행하는 것입니다. 스마트폰 화면 확인이 목적이라면 집 WiFi로 충분하므로, 외부 공개를 서두를 이유는 없습니다.
